# Admission read-lock boundary — disposable PostgreSQL prototype

**Test fixture only; NO CUTOVER.** Compares a narrowly scoped `SECURITY DEFINER` read-and-lock function with a shared advisory-transaction-lock scheme. Advisory locks require every writer, including future admin and maintenance paths, to obey the same convention; a direct SQL writer can bypass it. It may also allow untrusted sessions to hold a lock and deny service. The fixture instead uses a row lock on the policy record, which conflicting policy writes cannot bypass. This comparison does not establish a production architecture decision.

The generated function has a generated `NOLOGIN` owner separate from runtime and policy admin; owner gets schema usage, policy SELECT/UPDATE (needed by PostgreSQL for `FOR SHARE`) and membership SELECT only. Runtime gets EXECUTE, never membership/policy UPDATE. The function has fixed `search_path=pg_catalog`, explicitly qualified tables, no dynamic SQL or write operation, and PUBLIC EXECUTE is revoked. The role owner is not a production service identity and the ACL procedure is not deployment provisioning. Identifiers interpolated by the test setup are validated fixture-generated UUID names; the subject is a bound SQL argument.

Caller must already authenticate the Telegram identity: the prototype cannot prove that an arbitrary supplied ID belongs to a user and must not be exposed as an authorization endpoint. `SECURITY DEFINER` owner privileges remain sensitive; protect function ownership, role membership, definition, schema and credentials. A compromised migration owner or privileged policy writer is outside this fixture's boundary. No secure admin authentication, audit provenance, policy bootstrap, fleet rollout, rollback or D-04 decision is introduced.

The caller must hold a transaction around the function and the associated protected DB mutation. A `FOR SHARE` lock persists until commit/rollback; it must not span a provider POST or other external network request. A false decision is only data: trusted application code must deny before doing side effects. This fixture does not wire the function to Telegram, Mini App, `Pricing.confirm_once` or job creation and does not establish the existing global lock order. Existing Config admission remains active.

**Writer-bypass mitigation in fixture:** the trusted test operator has direct membership INSERT/DELETE, so the prototype adds a narrowly scoped `SECURITY DEFINER` trigger that acquires the same policy row's exclusive lock before each membership write. A test checks that direct deletion waits for an active policy read transaction. Trigger/owner tampering by privileged roles, real operator authentication, independently trustworthy audit and deployment grants remain blockers. The trigger cannot make direct changes audited or versioned: direct membership writes in this fixture bypass the version and audit API and must be prohibited in a deployable design.

The tests use real separate login roles and PostgreSQL connections. They exercise uninitialized and incomplete-policy failure, denied outsider, runtime mutation/DDL denial and `pg_temp`/search-path shadowing, an actual policy-lock → wallet-lock → existing `Service.movement` transaction with idempotent event key and rollback, a revoke waiting for the first transaction, revoke-first denial, CAS replay/concurrent writers, lock timeout, a deliberately inverted synthetic deadlock and two independent runtime subprocess reads. Deadlock detection/rollback in this constructed schedule does not prove the real application is deadlock-free. Real production roles, every possible inherited role, all endpoints, actual payment/provider integration and no-restart revocation through real Telegram/Mini App require further evidence. No network to Telegram or paid providers is used.

Setup creates a generated NOLOGIN role and function only in the disposable schema; it drops both on cleanup. Do not deploy it without a separate migration/role design, admin authentication, reviewed narrowly scoped audited control interface, reliable backup/restore grants and owner approval. Previous migrations, in particular 040, remain unchanged.
