# PostgreSQL admission candidate — isolated shadow primitives

Owner approved Option B as a direction: [decision](https://github.com/Burn2288/FLOW-BRIDGE-GEN/pull/37#issuecomment-6959636116). This Draft is **PARTIAL / CUTOVER_NOT_AUTHORIZED**. It does not enable authoritative admission, and the application continues to use its existing per-process Config. D-04, administrative control, retrieval, recovery and cutover/rollback decisions remain open.

Migration `040_admission_policy_shadow.sql` adds an uninitialized policy/version, separate admin/tester membership and change audit with idempotency key. It imports no env allowlist and changes no existing user, wallet, ledger or job. The candidate library has versioned CAS, immutable audit rows against ordinary UPDATE/DELETE, a transaction-scoped shared policy lock and a redacted shadow comparison. Its `enable_authoritative_policy()` always raises. Neither `shadow_compare` nor `require_on` is wired into real Telegram, HTTP, Mini App, quote or confirm: this is a testable API foundation, not a complete implementation of the owner-approved behavior. Shadow logging currently occurs only when explicitly called by a trusted test/integration caller; no live sampling is installed.

## Security blockers before using the candidate

- `replace_policy` accepts an injected authorizer for isolated tests; no non-forgeable runtime admin identity or privilege boundary exists. Existing default application-role privileges grant table DML, so the candidate's audit trigger alone does not prevent forged INSERTs, a privileged schema owner altering the trigger, or other direct unauthorized changes. Independent DB roles/grants, trustworthy admin authentication and immutable audit protections must be designed and reviewed before use.
- Membership decision assumes the caller has verified Telegram identity. Other platforms and public mode are not implemented by this policy store. Mini App sessions, old callbacks and all alternate entry points do not yet use the database policy. DB failures currently do not enforce fail-closed behavior in those existing routes.
- `require_on` serializes with updates only when called within the *same* protected transaction as the mutation. Tests demonstrate a synthetic policy-lock → wallet-lock transaction, not the real `Pricing.confirm_once`/job path. Establish and verify global lock order against `POLICY_LOCK`, wallet, job and existing callbacks before wiring; never hold the DB lock during a provider POST.
- Shadow mismatch logs contain only category, not ID/token/config, but there is no deployed observer, versioned event retention or production metrics. Centralized revocation without process restart is **NOT_IMPLEMENTED** in actual Telegram/Mini App; the existing independent-process #36 test only establishes legacy stale behavior.
- There is no validated migration cutover, audited bootstrap, rolling-deployment gate, safe rollback, finalized D-04 admin identity mapping, or handling for already paid outcomes. Authoritative enablement is blocked; dropping shadow tables or returning to old allowlists after future policy changes could restore revoked rights.
