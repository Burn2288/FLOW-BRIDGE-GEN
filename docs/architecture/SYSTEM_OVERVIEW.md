# Целевая архитектура

Направление для проверки после S0 — модульный монолит на Python и PostgreSQL с отдельными процессами HTTP API, Telegram gateway, worker и обслуживания. Границы ниже описывают проектное намерение. [Фактическая архитектура](../audit/AS_IS_ARCHITECTURE.md) фиксируется по исходникам.

- Telegram Gateway и Public API используют публичные операции Identity & Access, Generation Orchestration, Model Catalog, Billing и User Library. Mini App использует тот же backend.
- Generation Orchestration координирует Job Queue, Provider Integrations, Media Storage и User Library. Telegram-обработчики обращаются к публичным операциям модулей, без доступа к их внутренним таблицам.
- Billing & Ledger владеет финансовыми командами и проводками. Payments проверяет входящие события и передаёт идемпотентные команды в финансовый модуль.
- Admin Backend, Reports & Analytics, Observability и Runtime Configuration предоставляют управляемый доступ, диагностику и эксплуатационные параметры.

Для очереди сначала оценить PostgreSQL. Долговечная очередь требует атомарного захвата, lease, heartbeat и fencing token, ограниченных повторов, таймаутов, отмены, восстановления и ручной обработки. Ограничения параллелизма применяются атомарно по системе, провайдеру, модели, пользователю, типу задачи и подписке. Backpressure и ограниченный размер очереди защищают сервис от перегрузки.

CLODEX — первый адаптер. Адаптеры нормализуют результаты и ошибки, владеют настройками, каталогом, ценами, лимитами, health checks и политикой таймаутов. Маршрутизация учитывает возможности, доступность, стоимость, скорость, лимиты и политику пользователя. При неизвестном исходе платного вызова failover допускается только при доказанном отсутствии исполнения или безопасной идемпотентности.

Перед переносом кода согласовать правила зависимостей, владение данными и границы транзакций. Зафиксировать решения в ADR по мере принятия.
