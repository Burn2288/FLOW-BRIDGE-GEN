# Flow-Bridge-Gen — METHOD CORE
Комплексная инженерная реконструкция, коммерческая готовность и независимая архитектура
Роль: Principal Software Architect / Staff Backend Engineer / Distributed Systems Engineer / Security Engineer / SRE / QA Lead / Product Architect.
Режим: самостоятельная инженерная работа с обязательным аудитом, доказательствами, реализацией и независимой приёмкой.
Исходный проект: darkflow-gen-ubuntu, Python, PostgreSQL, Telegram, CLODEX, Platega, Telegram Stars, Ubuntu 24.04.
Приоритет: P0 — восстановить фактическую генерацию и доставку изображений. P1 — безопасная конкурентная обработка заданий. P2 — коммерческая архитектура, API, администрирование и эксплуатационная готовность.
0. ГЛАВНАЯ ЦЕЛЬ
Превратить существующий Flow-Bridge-Gen из частично работающего Telegram-бота в модульную, отказоустойчивую коммерческую платформу AI-генерации.
Будущий продукт должен поддерживать:
генерацию текста;
генерацию и редактирование изображений;
синтез речи и обработку аудио;
генерацию видео;
различные AI-модели и агрегаторы;
Telegram-бот;
Telegram Mini App;
отдельную административную панель;
платные подписки, кредиты и платежи;
историю и библиотеку генераций;
мониторинг, аналитику и отчётность;
расширение без переписывания ядра.
Запрещается считать задачу выполненной только после подготовки документов, тестовых заглушек или успешной компиляции.
Нужен работающий продуктовый срез.

3. P0 — ГЛАВНАЯ НЕИСПРАВЛЕННАЯ ОШИБКА: НЕ ПРИХОДИТ ИЗОБРАЖЕНИЕ
Это первоочередная задача.
Пользователь запрашивает изображение через Telegram и AI-провайдера, но не получает ожидаемый результат.
Прежние попытки исправления не дали подтверждённого результата.
3.1. Восстановить всю цепочку
Telegram update → обработчик → параметры модели → валидация → job → вызов CLODEX → ответ API → интерпретация результата → скачивание или декодирование → сохранение → регистрация в БД → Telegram sendPhoto/sendDocument → подтверждение доставки.
На каждом этапе проверить:
входные и выходные данные;
идентификаторы корреляции;
соответствие контрактам;
исключения и таймауты;
транзакции;
состояние задания;
файловые операции;
ответ Telegram.
Создать тестовый trace одной генерации, не раскрывающий секреты.
3.2. Исследовать все возможные причины
Проверить:
неправильный endpoint;
неправильный идентификатор модели;
некорректные параметры;
несовместимую схему ответа;
синхронный или асинхронный режим провайдера;
отсутствие ожидания завершения;
неправильную обработку data, url, b64_json и других подтверждённых форматов;
неправильный MIME;
ошибку декодирования base64;
невалидный PNG/JPEG;
недоступность URL изображения;
HTTP redirect;
ограничение размера;
ошибки записи в файловое хранилище;
ошибку транзакции БД;
блокировку event loop;
неправильный Telegram API-метод;
ошибки сериализации;
потерю результата при перезапуске.
Не предполагать, что API всегда возвращает готовый файл.
Подтвердить фактический протокол CLODEX на доступной версии API.
3.3. Исправить корневую причину
Требуется минимальный воспроизводимый сценарий:
Telegram → CLODEX → валидное изображение → постоянное хранилище → Telegram.
Добавить диагностику, позволяющую определить точный этап отказа.
Тестировать положительные и отрицательные сценарии.
3.4. Критерий приёмки P0
PASS допускается только при подтверждении следующего:
реальный запрос отправлен провайдеру;
получен реальный результат;
формат проверен;
результат сохранён;
Telegram подтвердил отправку;
пользователь получил изображение;
запись появилась в библиотеке;
после перезапуска результат остаётся доступным;
ошибка на каждом этапе не приводит к двойному списанию.
Требуется доказательство не менее трёх успешных последовательных генераций и одного сценария временного отказа.
Если живой тест недоступен, статус BLOCKED_LIVE, даже когда локальные тесты успешны.
4. P1 — МНОГОПОТОЧНОСТЬ, ПАРАЛЛЕЛИЗМ И НАДЁЖНАЯ ОЧЕРЕДЬ
Текущая система должна быть исследована на способность одновременно обслуживать множество пользователей.
Разделить понятия:
async I/O;
многопоточность;
multiprocessing;
конкурентное исполнение заданий;
горизонтальное масштабирование worker.
Не внедрять потоки без обоснования.
4.1. Требуемая модель
Пользователи должны иметь возможность одновременно:
отправлять сообщения;
запускать разные генерации;
пополнять баланс;
просматривать историю;
скачивать результаты.
Долгая генерация одного пользователя не должна блокировать остальных.
4.2. Очередь задач
Реализовать или укрепить:
durable queue;
atomic claim;
worker lease;
heartbeat;
fencing token;
controlled retry;
dead-letter / manual recovery;
timeout;
cancellation;
graceful shutdown;
restart recovery;
идемпотентность;
управление параллелизмом;
backpressure;
bounded queue;
персистентное состояние заданий.
Использовать существующий PostgreSQL, если он удовлетворяет требованиям. Redis, RabbitMQ и другие компоненты добавлять только при доказанной необходимости.
4.3. Ограничения параллелизма
Предусмотреть независимые лимиты:
глобальный;
по провайдеру;
по модели;
по пользователю;
по типу задачи;
по плану подписки.
Квоты должны проверяться атомарно.
4.4. Испытания
Провести нагрузочные сценарии на 10, 50 и 100 одновременных запросов в контролируемом тестовом окружении.
Использовать локальный эмулятор провайдера с управляемыми задержками, отказами и лимитами, чтобы не расходовать реальные кредиты.
Измерить:
throughput;
latency p50/p95/p99;
время ожидания в очереди;
долю ошибок;
потребление памяти;
нагрузку PostgreSQL;
число одновременных provider calls;
скорость восстановления после падения.
Отдельно проверить завершение worker во время платного запроса.

Разные модели могут принимать разные параметры.
Не создавать универсальную функцию с десятками необязательных аргументов.

5.3. Маршрутизация
В перспективе реализовать выбор провайдера с учётом:
доступности;
стоимости;

времени ответа;

Автоматический failover для платных запросов разрешён только при доказанном отсутствии выполнения исходного запроса либо при подтверждённой безопасной идемпотентности.
Не допускать двойной генерации и двойных расходов.
Подготовить тестовый адаптер второго независимого провайдера и доказать, что он подключается без изменения Telegram-логики и финансового ядра.
