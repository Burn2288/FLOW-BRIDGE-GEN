# CLODEX API — руководство интеграции

## 1. Предпочтительная архитектура
Telegram → Python Bot (aiogram) → Backend API → PostgreSQL (`users`, `orders`, `jobs`, `transactions`, `provider_requests`) → Queue Worker → ProviderAdapter (`ClodexAdapter` / `DirectElevenLabsAdapter`) → object storage → Telegram.

Рекомендуется модульный контракт провайдера:
- `capabilities()` — получить доступные операции и модели;
- `list_voices()` — список голосов;
- `synthesize(text, voice_id, model, format, settings)` — озвучка;
- `get_job(job_id)` — статус async задачи (если доступно);
- `convert_voice(file, settings)` — Voice Changer, только если API подтверждено;
- `dub(file, options)` — Dubbing, только если API подтверждено;
- `get_balance()` — только если доступен подтверждённый endpoint;
- `map_error(response)` — единые коды ошибок.

## 2. Конфигурация
- `CLODEX_BASE_URL`: первоначальный кандидат `https://clodex.xyz/v1`; подтверждается тестом.
- `CLODEX_API_KEY`: токен сервиса; только server-side.
- `CLODEX_TTS_MODEL`: **не заполнять до списка реальных моделей**.
- `CLODEX_TTS_PATH`: **не заполнять до официальной спецификации**.
- `REQUEST_TIMEOUT_S`: раздельно connect/read/total; TTS может занимать существенно дольше обычного JSON.
- `DRY_RUN=true` по умолчанию.

## 3. Последовательность подключения
1. Установить официальный base URL из кабинета/документации.
2. Создать отдельный минимально привилегированный API-ключ.
3. Безопасно получить список моделей (если метод документирован), записать модель ID и снимок ответа без токенов.
4. Получить точный HTTP contract функции TTS: method, path, headers, body, MIME response, варианты ошибок.
5. Согласовать бюджет одного платного теста и вручную включить его.
6. Отправить короткий текст с одним разрешённым голосом и проверить фактический аудиофайл (MIME + magic bytes + воспроизведение).
7. Сравнить usage/счёт до и после; зафиксировать фактическую цену операции.
8. Проверить ошибки: неверная модель, пустой текст, превышение лимита, 401, 429, 5xx (без затратных и опасных циклов).
9. Подключить Telegram-бота только после TTS LIVE PASS.
10. Подключить оплату после идемпотентных транзакций и подтверждённой себестоимости.

## 4. Транспорт / HTTP
- Один клиент, тайм-ауты и отдельные коды `AUTH_INVALID`, `RATE_LIMITED`, `PROVIDER_5XX`, `TIMEOUT`, `INVALID_RESPONSE`.
- Для 429/502/503/504 — ограниченное exponential backoff + jitter. **Не повторять платные неидемпотентные операции автоматически**, если неизвестно, выполнились ли они на стороне провайдера.
- Логировать `request_id`, endpoint, method, status, elapsed_ms, MIME, size, provider_request_id; без payload секретов.
- Если TTS возвращает binary/audio — сохранять bytes, не парсить как JSON; если JSON — проверять спецификацию результата.
- Сохранять raw provider response metadata и трассировку; пользовательскому боту отдавать нормализованную структуру.

## 5. Telegram и платежи
- `/start` → соглашение → выбор функции → текст → голос → предварительная цена → подтверждение → генерация → результат.
- Ограничение на размер текста; очередь; максимальная длительность запроса; квоты на пользователя.
- Платёж обрабатывать только через подтверждённое событие оплаты; идемпотентная запись `payment_id`.
- Проводки: зарезервировать баланс → выполнить задачу → списать по факту или вернуть резерв при подтверждённом провале.
- Для цифровых услуг внутри Telegram проверить актуальные требования Telegram Stars и действующие правила платформы.
- Клонирование голосов только при подтверждённых правах/согласии владельца голоса.

## 6. Что НЕ делать
- Не использовать прямой ElevenLabs SDK как клиент CLODEX без документированной совместимости.
- Не утверждать, что `/v1/audio/speech`, `/v1/audio/voices` или `/v1/text-to-speech/{voice_id}` точно работают на CLODEX.
- Не опираться на сторонние котировки цен как на подтверждённые списания.
- Не включать массовую генерацию и автоматический платный ретрай до проверки биллинга.
- Не передавать ключи боту, в браузерную консоль или в репозиторий.
