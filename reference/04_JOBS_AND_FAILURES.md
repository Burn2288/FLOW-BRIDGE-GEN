# Задания и восстановление

Статусы генерации: queued → dispatching → running → succeeded / failed / uncertain.
queued можно отменить с release. После dispatching отмена не обещается без поддержки провайдера. Delivery ведётся отдельно: pending → sending → sent / retry / expired.

Worker атомарно забирает queued, выставляет lease_owner, lease_until и attempt_id, фиксирует dispatching ДО сетевого вызова. claim не является доказательством отправки. После аварии в dispatching статус uncertain, если невозможно доказать отсутствие отправки. Из running/dispatching с истёкшим lease нельзя автоматически возвращать платное задание в queued.

Если API документирует async job: сохранить provider_job_id сразу; дальнейшее ожидание — безопасные status-запросы с backoff. Если поддерживается idempotency key, привязать к job UUID и повторять только по официальной гарантии и сроку хранения ключа.

## Ошибки
- Невалидный ввод до отправки: не резервировать либо освободить резерв.
- Документированный отказ без генерации: failed + release.
- Timeout/обрыв/5xx после возможной отправки: uncertain; резерв удерживается, новые платные повторы не выполнять.
- 429: повтор POST только при подтверждённом отсутствии исполнения или идемпотентности. Retry-After сам по себе не гарантирует отсутствие списания.
- 401/403: отключить провайдера и новые задания; результат уже отправленных запросов сверить.
- Готовый файл не прошёл проверку: сохранить метаданные, не отправлять; сверить результат/стоимость; при подтверждённой непригодности вернуть резерв по политике сервиса.
- Telegram недоступен/пользователь заблокировал бота: сохранить готовую работу, повторять только доставку.

## Успех
Проверить MIME, размер, сигнатуру и возможность прочитать длительность аудио. Записать временный файл с уникальным именем; atomic rename; сохранить file record и succeeded + capture одной DB-транзакцией. При сбое между файлом и БД не делать повторный provider POST: использовать сохранённый результат или uncertain/reconcile. Периодическая уборка orphan-файлов не затрагивает активные работы.

## Неопределённые операции
Проверить provider job/request ID, официальный endpoint, usage либо поддержку. Автоматическое разрешение только с доказательством. Администратор может принять убыток и вернуть клиенту резерв после установленного срока, но обязан отметить запрос как possibly_billed; старый результат не должен затем автоматически повторно списать клиентские средства.

## Доставка
Повторы ограничены, с backoff и jitter. Timeout отправки Telegram может означать уже доставленное сообщение: возможен дубль сообщения, но никогда дубль генерации/списания. История остаётся источником статуса.
