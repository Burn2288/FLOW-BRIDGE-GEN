# Совместная работа

| Ветка | Назначение |
| --- | --- |
| `main` | Общая база. Изменения входят через PR после ревью второго разработчика и успешных обязательных проверок на актуальном коммите. |
| `dev/burn2288` | Личный план Burn2288 и незавершённые изменения. |
| `dev/vankhu21` | Личный план vankhu21 и незавершённые изменения. |
| `work/<логин>/<задача>` | Один готовящийся к ревью срез. Ветка создаётся от актуальной `main`, в неё попадают только коммиты задачи. |

Личный план и черновые коммиты можно хранить в своей ветке. Репозиторий публичный, поэтому и личные ветки публичны. Ключи, пользовательские данные и приватные артефакты храните локально вне Git. Указывайте в личном плане ссылки на общую дорожную карту, критерии приёмки и PR. Если обе задачи касаются одного модуля, миграции или контракта, заранее согласуйте порядок изменений.

## Настройка на Windows или Ubuntu

Каждый разработчик выполняет команды на своей машине в выбранной родительской папке. Клонируйте проект один раз. Для существующего клона проверьте `git remote -v` и начните с `git fetch origin`.

```sh
git clone https://github.com/Burn2288/FLOW-BRIDGE-GEN.git
cd FLOW-BRIDGE-GEN
git config user.name "ВАШ ЛОГИН"
git config user.email "ВАШ ПОДТВЕРЖДЁННЫЙ EMAIL ИЛИ GITHUB NOREPLY"
git fetch origin
git switch --track origin/dev/vankhu21
```

Burn2288 в последней команде указывает `origin/dev/burn2288`. Если локальная ветка уже есть, переключайтесь через `git switch dev/<логин>`. Для публикации через Git используйте учётную запись с правом записи. Откройте корень клона в Codex. Используйте относительные пути проекта, отдельные локальные окружения и тестовые учётные данные.

Burn2288 подключает GitHub в своём Codex под `Burn2288`, vankhu21 — под `vankhu21`. Локальные `git config user.name` и `user.email` задают автора коммита. Для публикации из терминала отдельно нужна аутентификация GitHub на этой машине. Инструкции для Codex находятся в [AGENTS.md](AGENTS.md).

## Передача задачи между разработчиками

В начале задачи укажите в личном плане владельца, пункт общей дорожной карты, критерий приёмки и зависимости от работы коллеги. При передаче добавьте ссылку на PR, SHA проверенной версии и результат GitHub Actions. Если затронут общий контракт или миграция, отметьте, чей PR должен войти первым.

Начальные роли в S0–S1 согласуются по границе результата генерации. Burn2288 ведёт провайдера, запись результата и миграции. vankhu21 ведёт Telegram и сквозную проверку. Оба используют один correlation ID при разборе общего прогона и ревьюируют работу друг друга. Актуальные задачи остаются в индивидуальных планах.

## Цикл задачи

1. Перед началом сохраните незавершённые изменения в личной ветке. Обновите общую базу командами из раздела ниже. Проверьте личный план и согласуйте пересечения с коллегой.
2. Для публикации среза создайте `work/<логин>/<задача>` от актуальной `main`. При переносе из личной ветки перенесите только коммиты среза через `git cherry-pick`. Разделяйте коммиты плана и приложения.
3. Проверьте локальные тесты, контракты и сценарий отказа. Отправьте ветку в GitHub командой `git push -u origin HEAD` и откройте PR в `main`. Заполните чек-лист PR и приложите результаты к точному SHA.
4. Второй разработчик проверяет diff, риски и доказательства. После замечаний повторите проверки для новой версии. Слияние выполняется по согласованному решению команды после ревью и зелёных обязательных проверок. Сбой, пропуск или отсутствие нужной проверки останавливает приёмку соответствующей части.
5. После работы над задачей Codex синхронизирует весь клон на машине её автора. Задача считается принятой после слияния проверенного PR. Если PR ещё открыт, обновите локальную `main` до последней принятой версии и укажите статус ожидания в плане. На второй машине ту же процедуру выполняет Codex второго разработчика при начале следующей задачи или при приёмке.

## Синхронизация целого проекта

Сначала проверьте `git status --short`. Сохраните незавершённую работу в её ветке. Перед обновлением проверьте на GitHub принятые PR и результаты нужных проверок. В корне клона выполните:

```sh
git fetch --prune origin
git switch main
git merge --ff-only origin/main
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
```

Совпадение двух SHA подтверждает, что общая локальная копия включает принятые изменения обоих разработчиков. Если затронуты зависимости или схема БД, обновите тестовое окружение и выполните проверки по [инструкциям запуска](docs/operations/DEPLOYMENT.md). Сохраните SHA и результат в итогах задачи. Если fast-forward невозможен или SHA различаются, остановитесь и разберите расхождение. Чтобы продолжить личную работу, переключитесь на свою ветку, проверьте расхождения с её удалённой версией, затем при чистой рабочей копии влейте актуальную `main` командой `git merge main`. При конфликте сохраните обе версии и согласуйте решение. После слияния стартового PR ветки разработчиков также подтягивают `main`.

## Правила инженерной работы

Перед изменением архитектуры изучите исходники и существующие доказательства. Сохраняйте действующие возможности, меняйте по одному проверяемому срезу и обосновывайте новые компоненты. Для существенного изменения нужны тест, контракт и сценарий отказа. Ограничивайте повторы и не повторяйте платную операцию с неизвестным результатом. Для недоступного внешнего ресурса укажите `NOT_PROVEN` и приведите проверяемое описание блокировки.

Для обычных обратимых локальных действий Codex действует самостоятельно. Для списаний реальных денег, массовых платных генераций, изменений production-БД, разрушительных миграций, ротации действующих ключей, удаления пользовательских данных и публикации production-релиза нужно отдельное разрешение. В отчётах используйте обезличенные данные и отделяйте тестовые секреты от production.
